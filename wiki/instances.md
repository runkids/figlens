# Instance expansion

How `src/expand.rs` builds an instance's sublayers from its main: override and derived rows, component properties, constraint resizes and scale. Load this, with `fig-format`, before changing instance expansion; node ids and the `I<instance>;…` path rule are in [fig-format.md](fig-format.md).

## Expansion rules

Rules marked pending have local evidence; others are sweep-backed.

- `symbolData.symbolOverrides` and `derivedSymbolData` use the same guidPath keys; nested instances carry their own, relative to themselves. Merge **field by field** (outer wins per field): one list can hold several entries for the same path (e.g. a swap, then a size), and an outer derived entry may hold only geometry while the nested one holds the size. Whole-entry merging was the cause of what looked like footer design edits and an auto-layout gap (button 216→336); Figma does store those sizes. `overrideLevel` is not read and needs no ordering: across nine files (2026-10-28, #53), no list set one field twice for one path, and every outer entry with level ≥ 2 carried the same value as the nested instance's own entry.
- `componentPropRefs` binds assignments: SYMBOL_ID swaps instances, BOOLEAN sets visibility, TEXT_DATA merges source `textData` unless directly overridden (calibration pending). `overriddenSymbolID` also swaps. Swaps take the new main's visibility and name (a variant's set name), unless explicitly renamed.
- `derivedSymbolData` stores sizes only sometimes: SCALE/STRETCH constraint resizes must be computed (groups and boolean ops pass the outer resize through to their children), except for children in auto-layout flow (only ABSOLUTE-positioned ones follow constraints).
- Resized instance children: use derived `fillGeometry`/`strokeGeometry`/`derivedTextData` when present, else scale the source geometry by size / source size (fill and stroke separately).
- Pending (2026-11-09, local evidence): an instance scaled with the Scale tool (K) keeps its own size and stores `symbolData.uniformScaleFactor`; its main's lengths are drawn times that factor (`expand::SCALED`, `SCALED_PARTS`: radii, stroke and border weights, dashes, effect radius/spread/offset, auto-layout spacing and padding, grid gaps, min/max size, font size, paragraph and list spacing, pixel letter spacing and line height, and those of each `textData.styleOverrideTable` range; percent units and unit-box blur positions stay). Child sizes and translations scale too, and constraints fit from main × factor to the stored size; sizes within a millionth are equal, since an f32 factor times an f32 length is a few ulps off what Figma stored. The instance's own override and derived rows are already at its scale; a nested instance's own rows take the enclosing main's factor (their outlines keep the size they were drawn at, the node's size over that factor), and nested factors multiply (each in 1e-3..1e3, else ignored; products clamped). A text style linked by the node or one of its ranges takes the node's factor (`Expanded::scale`). Every derived field is used as written and wins over the override and the main, as size does, not only size, transform and outlines: Figma also derives scaled stroke weights, effects and spacing there, almost only on scaled instances. Evidence: in five community and production files, derived values equal main × factor (stroke weight 291 of 410, font size 5/5, effects 3/3; the 119 others are one icon's 17 instances); radii never appear in derived rows, so their rule follows the same model unchecked. Not scaled yet: per-point vector radii, layout grids, guides and image tile scale. Not compared with Figma's REST output yet.
- Variable-bound paints of instance sublayers must be resolved in the nearest explicit `variableModeBySetMap` mode (else the set's first mode); direct nodes' cached colors are already right. Library variable values are present in the `.fig`.
