# Host integrations

Load this for OpenCode V2, OMP, cross-host ownership, the shared npm package or installed-adapter acceptance. Pi-specific UI and mapping rules remain in [pi.md](pi.md); native MCP contracts remain in [mcp.md](mcp.md).

## Package and shared behavior

`npm/package.json` is the only public package, `@runkids/figlens`. Its CLI root retains CommonJS semantics. Pi and OMP manifests point to independent `pi/index.ts` and `omp/index.ts`; OpenCode exports point to `opencode/index.mjs`, `./tui` and `./rpc`. Each host imports only its own SDK. Optional peers describe host dependencies without raising the CLI's Node 18 floor. Use actual installed loaders to verify resolution; a manifest or rewritten Pi import is insufficient.

`pi/workflow.mjs` owns mapping state, validation, evidence freshness, locking and atomic publication. `pi/viewer.mjs` owns viewer startup/readiness and process cleanup. `pi/requests.mjs` reads the one shared skill/reference tree and builds open/preview/plan/YOLO/map requests. Adapters retain native schemas, UI, permissions and dispatch; no separate host framework or mapping format exists.

`prepare-npm.cjs` stages maintained `pi/`, `omp/`, `opencode/`, the shared skill and `omp/mcp.json` as root `.mcp.json`. Generated copies are ignored. Exact package inventory is checked in `check-installation.py`; tests, probes, private files and generated `.fig` fixtures are not shipped. Native archives and npm resources take guidance from the same sources. Keep version, launcher/cache/checksum handling and release pipeline shared.

Pi, OpenCode and OMP start `figlens mcp` without `--storage-root`, so they get the `index` and `jobs` tools unchanged: default storage and a location the user once chose with CLI `--storage` work there; a new custom `storage` in a host call is refused until the server gets that flag.

An index is opt-in in every host (user decision, 2026-10-30): an ordinary search reads the `.fig` directly and creates no database. When the user asks to enable an index for a design and scope, the shared skill has the agent `index` `prepare` it (no setup command), poll `jobs` until `succeeded`, `search` with `workspaceId` and `node` set to the prepared scope, and `inspect` the exact `ref.nodeId`; later searches, restarts and other hosts reuse that workspace. Natural language through the MCP `index` tool is the opt-in entry in every host; no host adds an index command. Adapters never resolve storage paths or open the database; the binary does. Per-action authorization uses each host's own mechanism:

| Host | Prepare, status, refresh, search | `reset`, `replaceUnavailable` |
|---|---|---|
| Pi | No built-in permissions | Same; `index` declares `destructiveHint: true`, which a Pi permission extension can read |
| OpenCode | Native tool/bash rules | `ctx.permission.assert` action `figlens_index`, resource `reset` or `replace_unavailable`: `execute.before` on `<mcp server>_index`, and inside `figlens_index` |
| OMP | MCP `write` tier, arguments shown | Same tier; no per-action rule, and the default `yolo` approval mode runs it |

OpenCode registers `figlens_index`, `figlens_jobs`, `figlens_search` and `figlens_inspect` (CLI path, `adapter.cli`, mapping in `cliArgs`) only when the user's server is disabled or named `figlens` (dropped by OpenCode), so a session never shows two copies of a tool. A CLI-path call that reads a design (search, inspect, prepare, add, relocate) first asks `read` on its requested and canonical path, as `Workflow.source` does (a `gs://` design is refused, since the CLI reads it from a download cache the adapter cannot authorize; MCP serves it), and a workspace search, `refresh` or `rebuild` asks it on the registered source paths `index status` reports (narrowed by `sourceId`), since a new session may deny a design an earlier one prepared; `prepare`, `refresh` and `rebuild` run in the foreground until their jobs finish, so they skip the 120-second command timeout. Before a CLI-path write, `adapter.cli` runs the read-only `index status` and asks `edit` on the reported workspace directory and its sibling `paths.lock` (the state root while it is absent; a binary that reports a workspace without `paths.lock`, or a lock recovery without `lock`, is refused as too old) plus `roots.config`, where every write takes a location lock or record; `jobs cancel` asks it for the workspace its `jobs status` reports, and recreation, whose `status` fails, for its new `storage` and that storage's `state` directory plus the `roots.config` that the failure's recovery actions name. Every one of these edit asks also covers the path's canonical destination: the `realpath` of its nearest existing parent plus the missing rest, starting from the unnormalized path and following a dangling link, because the binary canonicalizes the root before writing. When status fails on a lost lock (recovery offers `prepare` and `reset`) or an owned newer schema (`reset` only), the explicit action asks for the `path`, `lock` and `roots.config` of the failure's matching recovery action instead; any other failure is rethrown. A binary that reports neither field fails the call instead of guessing a path. A new custom storage over MCP needs a user server started with `--storage-root`; each host README says where to configure it. CLI-path tools return text content only: OpenCode rejects a structured `output` from a tool without an output schema. OpenCode also validates every MCP `structuredContent` against the tool's `outputSchema` and fails the call on a mismatch, which unit tests do not see; run the host lanes on the real runtime.

## OpenCode V2

Current local runtime evidence uses OpenCode 2.2.0. OpenCode is a Bun-built binary: `process.execPath` is the host, not Node, so `opencode/adapter.mjs` runs the bundled launcher with `node` from PATH (`launcherRuntime`). The CI harness sets `FIGLENS_BIN`, which skips that path; the unit test covers it. The server registers MCP/skill transforms, three model tools (seven on the CLI path, below) and the argument-taking `figlens` command. Native slash submission preserves files, agent/skill mentions and delivery; the server signals TUI review/frame dialogs through a typed RPC event. Human operations use `figlens-operation` and `figlens-review` RPC definitions. Noninteractive review leaves proposals pending. No model tool approves mappings.

Every operation checks that the host session's canonical directory matches the plugin location. Shared Workflow authorization checks dynamic source/code reads and writes; launcher execution, export paths, preview cache and owned temporary workspaces receive read/edit/bash authorization before side effects. Permission failure and cancellation remain errors. Review RPC keeps a 64 KiB request budget, complete pending evidence within a 4 MiB reply budget and the writer's field bounds. Authenticated clients are trusted; RPC context is not proof of human identity.

A session owns its Viewer and abort controller. Session deletion closes only that owner; project mismatch rejects operations and closes the old owner. Cancellation and timeout terminate and await the owned CLI process tree, including the npm launcher's native child, before reference cleanup. Session deletion and unload await those processes too. Plugin unload/reload aborts operations, closes all owned viewers, stops the event subscription and disposes registrations. Durable sessions outlive a TUI disconnect; disconnect is not permission to delete a session. Use `close` or delete the session to stop its viewer. Preview replaces the old viewer only after catalog/node readiness. URLs belong to the server machine; no tunnel is created.

The MCP transform installs a default under `figlensmcp` only when neither a `figlensmcp` nor a `figlens` configuration exists; status reports the key in use as `mcp.server`. OpenCode 2.2.0 drops every tool of an MCP server named `figlens`, the prefix of the plugin's own `figlens_*` tools, so the managed key must not be `figlens`. Existing local/remote/disabled settings remain unchanged. A managed default is ready only after connected status, its tools in OpenCode's tool registry (`mcp.catalog`; `connected` precedes the registry reload that puts them in a session's Code Mode catalog, so shortcuts wait up to 10 s for it, #125) and a matching same-package launcher version. It shares the local project directory and snapshot filesystem. Existing overrides whose handshake version/snapshot are unverified block dependent open/description-preview/map/plan/YOLO shortcuts; explicit local preview, manual selection, status, review and local tools remain available. Do not launch another MCP client or overwrite settings to hide an unverified state.

Manual selection exports a real PNG and TUI sends its bytes through the host file-attachment format with `resume: false`. Viewer tools return actual loopback URLs. File-content transport is distinct from image rendering or model consumption; no model run is implied by dispatch or attachment creation.

Before a reference export, Pi, OMP and OpenCode use `Workflow.referenceDirectory()` to reject symbolic `.figlens`/guide paths and a symbolic `.figlens/previews` directory before creating or exporting anything. Lexical project-path authorization does not authorize a symlink's external target; the native writer canonicalizes output parents. Keep the external-directory-denial regression for both parent and preview links, and the installed OMP command regression.

## OMP

Current production-entry evidence uses OMP 18.13.2 with Bun 1.4.3; earlier 18.12.3 results concern disposable probes. The entry uses OMP's injected zod schemas, own SDK/TUI, native read/write/exec tool approval tiers, same shared writer and native review dialogs. Commands are trusted extension code, as in Pi. OMP does not supply OpenCode's dynamic per-path permission assertion; tool approval tiers are not a filesystem sandbox.

Each session has a Viewer/lifetime. Switch and shutdown abort/close those resources. Each tool call creates a Workflow authorization closure containing its own cancellation signal; caching a closure with only the session signal loses cancellation on cached reads and writes. Keep the native-wrapper cancellation regression in installed acceptance.

The host discovers the packaged root `.mcp.json`, substitutes `OMP_PLUGIN_ROOT`, and uses `omp/mcp.cjs` to forward stdio/argv/exit/signal to `FIGLENS_BIN` or the adjacent CLI wrapper. Descriptor cwd is the package, so MCP arguments must use absolute session/project paths. Native user MCP configuration takes priority over package discovery; disabled/remote overrides are never connected by the test harness.

The public API exposes tool metadata, not the effective server configuration, handshake version or live client. Its `invokeTool` delegates only to the same native built-in. Under the current strict verification policy, MCP-dependent shortcuts report unverified state instead of dispatching. This also affects the default descriptor because the entry cannot prove whether an override replaced it. Local preview, frame selection, status, bindings, proposals, native review and the shared skill still work. Ordinary conversations may use the host-managed MCP. This is a documented partial integration, not full Pi parity.

## Acceptance

`npm test` checks shared state, cancellation, native review logic, ownership, override preservation and exact maintained staging. `scripts/check-installation.py` installs an extracted candidate tarball in a fresh consumer, verifies cold/warm/parallel launcher behavior and native/wrapper MCP (`mcp_smoke.check_mcp` also runs `search`, opens its exact ref with `inspect` and runs `diff` on two copies of the fixture, which must be two sources with no changes and complete: wiring evidence, not the revised-pair engine; Pi's registered MCP command uses the same check). `mcp_smoke.check_first_use` then starts the native, wrapper and Pi MCP commands from clean roots each: no state from connect, list, find or stateless search; concurrent prepare joins one database; cancel, restart reuse, `clear_cache`, `rebuild`, `reset` and re-prepare keep the source and other workspaces; a missing remembered root and (non-root POSIX) read-only storage fail with recovery. `check_reuse` then starts the wrapper on the native run's roots and searches that workspace without preparing (cross-host reuse). The report's `firstUse` lists what ran or was skipped. It then optionally runs host profiles. Existing CLI Node 18 and Pi 1.3.0/1.4.0 lanes remain.

- OpenCode: `--opencode-bin <binary> --opencode-sdk <@opencode/client-root>` runs `check-opencode-integration.mjs`, including real server/TUI, managed MCP, a scripted session lane (a test-only plugin registers a loopback OpenAI-compatible provider whose fixed Code Mode `execute` calls run `search`, then `inspect` on the returned `ref.nodeId`, then `diff` on two copies of the fixture; routing evidence, not a model; the session starts only after the managed tools reach the registry, recorded as `catalogAfterConnectedMs`, so an empty first search fails, #125), PNG bytes, permissions, mapping round-trip, two viewer owners, session deletion and reload. First-use lanes, also scripted: no `figlens` state after connecting, listing and stateless search; prepare, job polling, workspace search and inspect through managed MCP; a `figlens_index` deny rule keeping the database while an allow resets it; and, after a reload with a disabled user override, the same flow through the CLI-path tools.
- OMP: `--omp-sdk <@oh-my-pi/pi-coding-agent-root> --bun <binary>` runs `check-omp-integration.mjs`: real loader/approval wrapper, descriptor/bridge MCP (including `search`, `inspect` of its exact ref and `diff` of two copies, and first use: no state from connecting, prepare, job polling, workspace search, inspect, and OMP's own approval decisions for a reset), override priority, cancellation, native TUI review and viewer switch cleanup.
- Both profiles use `FIGLENS_BIN` pointing to the verified candidate binary. The same candidate's default wrapper cold path is checked separately by CLI/Pi tests; do not label a native override run as a cold adapter download.

The mapping case is original synthetic input generated at test time, not a Figma export or accuracy oracle:

```sh
mkdir -p samples/plugin-research/fixtures
docker compose run --rm dev cargo run --locked --example mapping-fixture -- samples/plugin-research/fixtures/mapping.fig
```

The generator refuses an existing output. CI's `host-installation` job starts it in the background while the host SDKs install, and never uploads the result. Public `examples/first-success/design.fig` remains the only distributable design fixture. Writer mocks, native synthetic parsing, real installed host/UI, image transport, actual model results and platform results are separate evidence. No-model acceptance never calls providers or reads user credentials/global plugins. Model plan/YOLO acceptance requires separate usage authorization; keep it untested until authorized. Local macOS acceptance does not prove Linux/Windows native TUI support or future CI success.
