# Stale-context hooks

`pi/stale.mjs` is shared. A target is recorded only from a successful `watch` `subscribe` (its reply's `subscription.subscriptionId`; a reply without one records nothing) or `ack`, including one without an action (tool names `mcp__figlens__watch`, `mcp__figlens_watch`, `figlens_watch`, `figlensmcp_watch`), with exactly its `workspaceId`, `subscriptionId` or `consumer` with `sourceId`/`scope`, and `storage`. `unsubscribe` by `subscriptionId`, or by `consumer` and `owner`, removes subscriptions; `forget` removes that consumer's raw views, an omitted `sourceId` or `scope` matching any, as the binary does; `start` alone records nothing because it has no checkpoint. A session keeps 32 (`KEPT`) and counts later ones as not kept; a target, restored or new, keeps only those selector fields, each at most 512 UTF-8 bytes (`SELECTOR_BYTES`) without C0/C1 control characters or line separators, or is not kept and counted. A whole target is at most 2 KiB serialized (`TARGET_BYTES`), and a fact cut down to fit keeps that whole target, never a shorter selector that would name a wider checkpoint. Selector lengths are counted in UTF-8 without copying the string. Only subscribe and ack register, because only they name a checkpoint; a `watch` `start` lease alone gets no note. OMP's reminder lists every kept target until `unsubscribe` or `forget`, since nothing there reads checkpoints. The checkpoint stays in the workspace database and moves only on an explicit ack. Before a user prompt four targets are checked with `changes ... --limit 1` under one 4 s deadline (`DEADLINE`), starting each turn after the last turn's four so every target is reached; the rest, failures and the deadline are listed as unchecked, a failure with the binary's `recovery` (`event_gap` among them). The note is data in a fenced JSON block: unread `revisionId` (a baseline marked as no design change) or query `evaluationId`, `refreshRequired`, `trackingTruncated`, a subscription state (`target_missing`, `identity_uncertain`), tracking state or evaluation that is not current. A run that ignores the batch signal, such as one waiting on a permission question, is still cut off at the deadline. Each fact stays within 4 KiB (summary, recovery and tracking rows give way, then `factTruncated`) and the note's facts within 16 KiB (`NOTICE_BYTES`), later facts counted as omitted. Pi reads each reply through `bounded`, because `pi.exec` buffers everything. It runs `reader()`: `FIGLENS_BIN`, else a bundled package's version-matched cached native binary (the launcher's own target, as OpenCode's watch holder does), so killing it stops the reader on Windows too. Past 64 KiB of stdout, on abort or a spawn error it kills the child (its process group outside Windows), and it rejects only once the child has exited, or reports that it could not stop it within 2 s; Pi's session shutdown and session changes wait for running readers. Only stderr's last 8 KiB is kept. Evidence so far is macOS: Windows and Linux run in the installed lanes; OpenCode's reply comes through `adapter.cli`'s 64 MiB buffer. The note joins that run's model calls and never enters the session, so a processed or revoked target leaves no copy and compaction cannot drop it.

| Host | Hook | Check runs with | Targets kept |
|---|---|---|---|
| Pi 1.4.0 | `tool_result`; `before_agent_start` for user prompts (a `custom` run keeps the last note); `context` | `bounded` run of the native binary its own MCP server runs, which has no `--root`; up to four in parallel | `appendEntry` `figlens-watch-targets` on the session branch, restored on `session_start` and `session_tree` |
| OpenCode 2.2.0 CLI path | `tool.hook('execute.after')`, `session.hook('prompt')`, `session.hook('context')` system part | `adapter.cli` `changes`, one at a time so one read permission question is open, asking its read and bash permissions every time; a question still open at the deadline stays open, but its answer starts nothing | Memory per session, dropped on `session.deleted` |
| OpenCode through MCP, OMP 18.13.2 | Same hooks; OMP `tool_result`, `context` | Nothing: an extension cannot see the server's `--root` (OMP 18.13.2's `ExtensionAPI` and `ExtensionContext` expose no MCP server configuration, only `mcp_notification`), so the note is a reminder to call `changes` | OpenCode memory; OMP `appendEntry`, restored on `session_start`, `session_switch` and `session_tree` |

Checks run before each user prompt, not between the tool calls of one run: no hook in these SDKs can run the check with the tool's authority mid-run without blocking it, so a long run relies on the agent reading `changes` itself.

Acceptance: `check-pi-integration.mjs` (hooks dispatched by the SDK's own `ExtensionRunner` on the 1.3.0 floor and 1.4.0: unread-free subscription, `refreshRequired` after a stamp change, no notice in the session, resume, cleared after refresh), `check-omp-integration.mjs` (reminder, failed call ignored, not persisted, restore, `forget`) and `check-opencode-integration.mjs` (CLI-path note in the scripted provider's system messages; managed-MCP reminder after a Code Mode `execute` acks a consumer, so `execute.after` sees the inner `figlensmcp_watch` call).
