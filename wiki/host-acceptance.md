# Host acceptance

How the installed-host lanes check each host entry from one extracted npm candidate; the entries themselves are in [integrations](integrations.md).


`npm test` checks shared state, cancellation, native review logic, ownership, override preservation and exact maintained staging. `scripts/check-installation.py` installs an extracted candidate tarball in a fresh consumer, verifies cold/warm/parallel launcher behavior and native/wrapper MCP (`mcp_smoke.check_mcp` also runs `search`, opens its exact ref with `inspect`, runs a file `usages` and runs `diff` on two copies of the fixture, which must be two sources with no changes and complete: wiring evidence, not the revised-pair engine; Pi's registered MCP command uses the same check, which is Pi's `usages` acceptance). `mcp_smoke.check_first_use` then starts the native, wrapper and Pi MCP commands from clean roots each: no state from connect, list, find, stateless search or stateless `usages`; workspace and library `usages` after the build; `index track`, its `changes` baseline and a `watch ack` that leaves the next poll empty; a `watch` `start` another host's `status` shows as not `mine`, ended `released` once the holding host's input ends; concurrent prepare joins one database; cancel, restart reuse, `clear_cache`, `rebuild`, `reset` and re-prepare keep the source and other workspaces; a missing remembered root and (non-root POSIX) read-only storage fail with recovery. `check_reuse` then starts the wrapper on the native run's roots and searches that workspace without preparing (cross-host reuse). `check_directory` starts Pi's registered MCP command from clean roots, prepares one of 11 designs in a project directory, then adds the directory with `index` `add`, passing each `nextCursor` back as `cursor` until it is null (10 then 1); every listed source has its canonical path, the prepared one keeps its id, and `index status` lists exactly those sources. Pi has no built-in permissions, so this lane checks no ask. `check_question` (with the mapping fixture) has that command prepare two copies in one project workspace, `watch` `subscribe` a text question over both as a fixed `sources` set, read the first evaluation with `changes` (both members' exact `0:1` refs), then replace one copy with the public design, `index` `refresh` and `watch` `evaluate`: `source_changed`, `changedSourceIds` naming only that member and `leftTopK` exactly the ref (old `snapshotId` included) that first entered. Model-free, it also checks that the native, wrapper and Pi MCP commands find `figlens-embed` beside `figlens` (OpenCode and OMP launch the native one): `models configure` with an empty model directory fails on the model, never on a missing runtime, and configures nothing; the cached companion matches `companionSha256` and answers `--version` and `--help`. The report's `firstUse` lists what ran or was skipped. It then optionally runs host profiles. Existing CLI Node 18 and Pi 1.3.0/1.4.0 lanes remain.

- OpenCode: `--opencode-bin <binary> --opencode-sdk <@opencode/client-root>` runs `check-opencode-integration.mjs`, including real server/TUI, managed MCP, a scripted session lane (a test-only plugin registers a loopback OpenAI-compatible provider whose fixed Code Mode `execute` calls run `search`, then `inspect` on the returned `ref.nodeId`, then `diff` on two copies of the fixture; routing evidence, not a model; the session starts only after the managed tools reach the registry, recorded as `catalogAfterConnectedMs`, so an empty first search fails, #125), PNG bytes, permissions, mapping round-trip, two viewer owners, session deletion and reload. First-use lanes, also scripted: no `figlens` state after connecting, listing and stateless search; prepare, job polling, workspace search, inspect, workspace `usages` (same `sourceId` as the search) and a library `usages` through managed MCP; the same 11-design directory add, page by page until `nextCursor` is null, in one Code Mode `execute`, under a `figlens_index` `reset` deny rule that an add, not being destructive, does not meet; the same two-source question, subscribed and read in one `execute` and evaluated after the replacement and a refresh in the next, under a `read` deny on the replaced member that managed MCP, asking nothing per `watch` action, does not meet; a `figlens_index` deny rule keeping the database while an allow resets it; and, after a reload with a disabled user override, the same flow through the CLI-path tools, then `track`, a `changes` baseline, its `watch ack`, an empty `changes` after it and a library `usages`. The CLI-path `figlens_index` directory add asks `read` on each page's listed files before it registers them: a deny on the second page's one file refuses that page and leaves 10 sources, and allowed, the cursor registers it. The CLI-path two-source question subscribes and pages through `figlens_watch` and `figlens_changes`; after the replacement and a `figlens_index` refresh, a `read` deny on the replaced member refuses `evaluate`, and allowed, it names that member. With that override, `figlens_watch` `start` under a denied `read` starts no lease, `status` works under a denied `edit`, one session's lease records a save the plugin's `figlens_changes` then shows and its own `stop` releases, a repeated `requestId` returns the same lease, another session's `stop` of it is refused, and session deletion or a reload releases a held lease. A consumer the session acknowledged is then checked before a later prompt: no note while it is current, a data note with `refreshRequired` after the fixture's stamp changes. Through managed MCP, a consumer acked inside a Code Mode `execute` gets the explicit-check reminder in the next prompt's system text.
- OMP: `--omp-sdk <@oh-my-pi/pi-coding-agent-root> --bun <binary>` runs `check-omp-integration.mjs`: real loader/approval wrapper, descriptor/bridge MCP (including `search`, `inspect` of its exact ref and `diff` of two copies, a library `usages` after an `index` job, the 11-design directory add followed through `nextCursor` with its sources matching `index status` `always-ask` prompting for the `add` and the default `yolo` allowing it, the two-source question with `watch` `subscribe` at the same tier, and first use: no state from connecting, prepare, job polling, workspace search, inspect, workspace `usages`, `track`, a `changes` baseline and its `watch ack` at the `write` tier, a `watch` `start` the bridge's disconnect ends `released` (on Windows `released` or the 30 s crash `expired`, as reported), and OMP's own approval decisions for a reset), the stale-context reminder of an acknowledged consumer, override priority, cancellation, native TUI review and viewer switch cleanup.
- `--host-watch-only` passes `--watch-only=<public design>` to both profiles: only the OpenCode watch/stale checks (managed-MCP reminder, `figlens_watch` lease and save, CLI-path note) and OMP's loader, bridge first use (track, ack, and the lease OMP's disconnect ends) and stale reminder, with no mapping fixture. OMP signals the server on POSIX, which in this uncontended lane must end the lease `released` (a forced kill under write contention would leave it to expire); on Windows it kills the bridge with TerminateProcess, so the report's `watchLeaseOnDisconnect` says `released` (the native server read stdin's end first) or `expired` (the 30 s crash fallback). CI's `host-watch` job runs it on macOS and Windows with the official OpenCode v2.2.0 assets checked against their release sha256.
- Both profiles use `FIGLENS_BIN` pointing to the verified candidate binary. The same candidate's default wrapper cold path is checked separately by CLI/Pi tests; do not label a native override run as a cold adapter download.

The mapping case is original synthetic input generated at test time, not a Figma export or accuracy oracle; with `--library` its Button main is a cached library copy (`synthetic-library`/`synthetic-button`, overridable by `MAPPING_FIXTURE_LIBRARY_KEY`/`MAPPING_FIXTURE_COMPONENT_KEY`; default output unchanged), so each lane names the library reference from an outgoing `usages` result and asks it (`check_library` for native, wrapper and Pi MCP):

```sh
mkdir -p samples/plugin-research/fixtures
docker compose run --rm dev cargo run --locked --example mapping-fixture -- --library samples/plugin-research/fixtures/mapping-library.fig
```

The generator refuses an existing output. CI's `host-installation` job starts it in the background while the host SDKs install, and never uploads the result. Public `examples/first-success/design.fig` remains the only distributable design fixture. Writer mocks, native synthetic parsing, real installed host/UI, image transport, actual model results and platform results are separate evidence. No-model acceptance never calls providers or reads user credentials/global plugins. Model plan/YOLO acceptance requires separate usage authorization; keep it untested until authorized. Local macOS acceptance does not prove Linux/Windows native TUI support or future CI success.

## Three separate evidence layers

- **A: installer logic.** `npm/cache.test.js` uses the existing VM injection with controlled tiny responses and extraction results. It checks cold/warm caches, HTTP/checksum/extraction/missing-tar failures, successful retry, preservation of an older valid cache and deterministic concurrent first use. These are branch tests, not real release-download evidence.
- **B: candidate artifacts.** `scripts/build-dist.sh` builds release-format archives in `Dockerfile.dist`'s digest-pinned toolchain. `scripts/pack-candidate.py` stages maintained resources into a new temporary package and runs real `npm pack`, not dry-run. `candidate.json` binds the commit, dirty state, source digest, tarball hash, archive hashes and native binary hashes. The installation check rejects another commit or different bytes.
- **C: published artifacts.** Not exercised by the candidate job. It never creates a tag, publishes, or downloads an older release just because its version string matches. A published-asset check requires a separately selected existing release/version; candidate passes are not evidence for that layer.

The test-only `scripts/candidate-fetch.cjs` intercepts the installed wrapper's two exact release-asset URLs using Node's preload mechanism. It serves the candidate archive and its real SHA256SUMS from disk, rejects every other URL, and counts requests. The wrapper remains unmodified: checksums, actual system `tar`, staging, atomic publication and subprocess startup all run. On Windows the wrapper explicitly uses `%SystemRoot%\System32\tar.exe` (built-in bsdtar) so a GNU tar earlier on PATH cannot break ZIP extraction. The preload is not packaged, changes no product configuration and provides no checksum bypass.
