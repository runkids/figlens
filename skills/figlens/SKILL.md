# figlens

`figlens` reads a `.fig` file (Figma: **File > Save local copy**) and prints REST-shaped snapshot data for a node: layout, text, styles, variables, instances already expanded. It also renders any node and writes a **bundle**: one zip with everything needed to build a frame. The `.fig` is a **snapshot**: it shows the design as it was when saved, so a newer design needs a newer copy.

figlens reads the design; the agent builds the frontend. figlens supplies what the design is: structure, values, components, variables, assets and reference pixels. Turning that into the product is frontend engineering, and it is yours: components, data, semantic and accessible markup and intent-based layout; web performance (image formats and sizes, font loading, layout stability, what ships to the browser); and the project's infrastructure (its framework, build, routing, asset and deployment pipeline). Use figlens as the design source for those decisions, never as a substitute for them.

## Setup

**With a loaded figlens integration:** use its registered figlens MCP tools (`tree`, `find`, `search`, `usages`, `diff`, `inspect`, `nodes`, `variables`, `bundle`, `export`, `export_batch`, `compare_image`, `freshness`). Pi, OpenCode V2 and OMP supply host-specific entries from one package; check the tools actually available in this session. A host may preserve an existing MCP override whose version or snapshot is unverified; report its unavailable shortcuts rather than treating it as ready. No global CLI, shell `npx`, `/figlens open`, or saved selection is needed for available MCP tools. The CLI examples below describe equivalent operations: pass each argument through the corresponding tool schema, using absolute `file` and output paths. The host supplies the namespace.

**Other agents:** use configured figlens MCP tools when available, or the CLI below.

**MCP without a local skill installation:** the server's `workflow` tool returns built-in guidance from this same skill. Choose `build` for design reading and project reuse, `audit` for comparing existing UI with a design and correcting confirmed differences, `images` for website asset preparation, `search` for an index, `usages` and following changes (build and audit carry only its decision table), `plan` for scoped planning, `planning-details` for page/multi-page work or unresolved dependencies, and `yolo` only for explicitly requested autonomous implementation and cleanup of what the run created. These are read-only guides, not commands that implement or verify a project. Follow `workflow:` links by requesting their topic from the same tool. Project edits, browser checks and filesystem permissions belong to the host agent.

Prefer `npx @runkids/figlens` for one-off use (Node.js 18+, no global install). The examples below use `figlens` as shorthand: replace that prefix with `npx @runkids/figlens` when no standalone binary is installed. The first run downloads and verifies the matching native binary; later reads use its local cache.

Other installation options (no Rust or Docker needed):

```sh
curl -fsSL https://raw.githubusercontent.com/runkids/figlens/main/scripts/install.sh | sh   # macOS, Linux
irm https://raw.githubusercontent.com/runkids/figlens/main/scripts/install.ps1 | iex       # Windows PowerShell
npx @runkids/figlens --help                                                                 # or run through npm
```

## Search and local index

Finding something in a design needs no index. Decide by what the user asked:

| The user asks | Do | Creates |
|---|---|---|
| Find copy, a layer or a screen, once or many times | `search` with `file` (CLI `search <file.fig> <query>`), then `inspect` the exact `ref.nodeId`; when an index may already be enabled for it, check first as below | nothing |
| Where a component, variable, style or image is used, or what a layer points at | `usages` as in Where it is used below (a library one across a prepared workspace: `library` there); when an index may already be enabled for it, check first as below | nothing |
| To enable, create or keep an index for a design or a project, for a scope | the opt-in steps below | one workspace in figlens storage |
| What changed between two saved copies, or since an earlier check | `diff` on the two copies (CLI `diff <old.fig> <new.fig>`); a scope an enabled index already tracks can instead be read with `changes` as below, without tracking anything | nothing |
| To follow a design's changes from now on | Following changes below; the request is the opt-in | a workspace if none covers it, and change history in it |

The index steps, their maintenance and failures, semantic and image search, Where it is used and Following changes are in [the search workflow](references/search.md); read it before calling `usages`, `index`, `jobs`, `changes` or `watch`.

## Where outputs go

`export`, `bundle`, `preview --out` and MCP `nodes` with `out` write only where you point them. Choose by purpose:

- A path the user names wins.
- Assets the site ships go where the project keeps its assets, following its conventions (see Images and slices).
- Files for your own checking (bundles and their extracted files, `nodes` JSON, reference images, comparison screenshots, scratch SVGs) go in a directory per task under `.figlens/exports/` at the project root, such as `.figlens/exports/<scope>/`, never loose in it, beside the plans and previews figlens keeps in `.figlens/`. When creating it, add `.figlens/exports/.gitignore` containing `*`: the directory stays out of Git without editing the project's ignore rules, while `.figlens/component-mappings.md` and `.figlens/sources.json` are still committed.
- Do not write beside the `.fig` or elsewhere in the project unless the user asks.
- The search index is not a project output: figlens keeps it in the per-user figlens state directory, or under the `--storage DIR` an earlier prepare remembered, never in the project or `.figlens/` on its own (see [Search and local index](#search-and-local-index)).

Over MCP, `out` is absolute and must be inside the configured roots; `.figlens/exports/` under the project root is.

## Refreshing a saved copy

A `.fig` is a snapshot of the moment it was saved. Refresh it when `freshness` says `stale`, when a mapped file is missing, or when the user says the design changed since the save. Never refresh to make a lookup pass that `freshness` called `current`: then the design really lacks it.

1. **Choose the route.** A design listed in `.figlens/sources.json` can be pulled: `figlens pull --only <name>` (repeat `--only` for several), or `figlens pull --stale` for every outdated or missing copy (needs `FIGMA_TOKEN`). A design not listed needs the user's **File > Save local copy**; offer to add it to the mapping for next time. Bare `figlens pull` downloads nothing and lists each design's freshness, so run it to show the user what would change.
2. **Ask first.** A pull opens Figma with the user's own account, so propose the exact command and run it only once they agree. It is CLI only (no MCP tool) and must run in a shell on the user's machine, where their Chrome is; from a remote host, CI or with no shell, give them the command instead.
3. **Sign-in is the user's.** With no saved session, or an expired one, a Chrome window opens on Figma's login page and the pull waits up to 10 minutes. Tell the user to sign in there and wait; never type credentials, click in that window or read its cookies. Mention that signing in there may sign them out of Figma on another device. `figlens pull --login` signs in ahead of time, for example before a long `--stale` run. `figlens pull --logout` deletes the browser profiles (signing figlens out); run it only when the user asks to sign out or reset that login.
4. **Read the report.** Each design is `pulled` (with the new `savedAt`), `skipped` (`current`, or why its staleness is unknown) or `failed`, and the command fails when any design failed. A failed design keeps its old copy untouched, and its `stage` says what to do:

   | `stage` | Meaning | Next step |
   |---|---|---|
   | `open`, `editor` | The file did not open: no access, a wrong link, the network, or Figma's CDN refusing | Ask the user to open the link in their browser; fix the mapping's `url` if it is wrong |
   | `menu` | File > Save local copy was not found or is disabled: a non-English Figma UI, a changed menu, or no export permission | Ask for a manual **File > Save local copy**; do not retry |
   | `export`, `download` | Figma did not deliver the file in 10 minutes, or the download broke | Retry that design once; large files with many images are slow |
   | `install` | The download is not a readable `.fig`, has no saved time, or is older than the current copy | Report it; do not retry or replace the copy by hand |

   Before the browser opens, the command refuses an unknown name, a mapped `file` outside the mapping's folder (`..` or an absolute path), a name mapped twice and a URL without a Figma file key; fix the mapping with the user. "pull needs its browser helper" or "playwright-core" means the npm install is missing: `npm i -g @runkids/figlens playwright-core`, or the agent-browser CLI on `PATH` instead. With both installed, playwright-core is used unless the command passes `--browser agent-browser`; each browser keeps its own login, so switching asks the user to sign in again. "another figlens pull is running" means wait for it.
5. **Continue on the new copy.** The pull replaces the mapped file in place, so repeat the lookup that failed on the same path. Leave figlens's state folder (the browser profiles with the user's login) alone.

## Building a frame

Building a frame is frontend work: the result is the code a senior engineer on the project's stack would write by hand from this design, with components, data, semantic markup and intent-based layout, delivered fast (sized images, loaded fonts, stable layout) through the project's own build, routing and asset pipeline. figlens supplies the evidence (structure, values, assets, reference pixels); it is never the code, the data or a runtime to ship. The quality bar: components with props, styling through the project's system and tokens, text as text, the project's own checks passing. An instruction to keep code minimal cuts scope and features, never this bar.

1. **Get the `.fig`.** Look for one in the project first; with a Figma link, try the `.fig` whose name resembles the link's file-name segment and confirm the link's node is in it (`figlens inspect <file.fig> <link> --depth 0`); when several or none fit, list them and ask. Ask the designer for File > Save local copy when there is none. For a `gs://` handoff, follow the [GCS snapshot cookbook](https://github.com/runkids/figlens/blob/main/wiki/gcs.md) for authorized access, refresh and preview limits. When there is no saved `.fig` and the user copied a selection in Figma instead, run `figlens clipboard .figlens/exports/<scope>/copied.fig` in a shell on the user's machine (it reads that machine's clipboard; with no shell, ask the user to run it); it keeps the source ids and used components but carries no image bytes or vector outlines, so treat its `missingImages`, `layersWithoutOutlines` and export warnings as missing inputs and ask for a saved `.fig` when they matter. Done when the file opens: `figlens tree <file.fig> --depth 1` lists its pages. When a linked node is not found, or `find` for a screen the user named returns nothing, run `figlens freshness <file.fig>` (MCP `freshness`) before reporting the design as lacking it: `stale` means the online file changed after the save: refresh the copy as [Refreshing a saved copy](#refreshing-a-saved-copy) says, then look again; `unknown` with `no_token` means it could not be checked (a `FIGMA_TOKEN` with scope `file_metadata:read` enables it). A read command's error that says the online file changed, or a `find` reply carrying `freshness`, is that same `stale` answer, so act on it without calling again. With `not_mapped` and the user's Figma link, run `figlens freshness <file.fig> --url <link>`; to make later checks and these hints automatic, offer to add `{name, url, file}` to `.figlens/sources.json` at the project root (`file` relative to that root, wherever the copy lives) and write it only once the user agrees. `unknown` never proves the copy current.
2. **Find the node yourself.** A Figma URL (`...?node-id=12-345`), `12-345` and `12:345` all work as-is. `inspect` returns `path`, the node's ancestors from the document down (for a layer, `path[1]` is its page), so a pasted link's page and screen need no `find`. Without one, use `figlens find <file.fig> "screen name" --type FRAME` or search visible copy with `--type TEXT`. Search is a case-insensitive substring over stored layer names and text; `--node <id>` scopes it and `--limit N` sets 1-200 results (default 20). Inspect candidate paths, dimensions, visible copy and reference renders to resolve the user's intent. If ambiguity remains, ask once with a short list of recognizable page/screen names and their differences or images. Resolve IDs internally. `truncated: true` means refine or scope the search. `find` sees stored layers only; to find copy that lives in instance overrides, text or boolean properties or swapped components, use `figlens search <file.fig> "words"`: ranked results carry exact `ref.nodeId`s (including `I<instance>;…` sublayers) for `inspect`, the match reason, and `coverage`; `coverage.complete: false` means a budget stopped the scan, not that the text is absent. To find where a component, variable, style or image is used, or what a layer points at, follow [Where it is used](references/search.md#where-it-is-used). Page with `nextCursor`; add `--include-hidden`/`--include-internal` only when asked. Instance children appear only after expansion: use `figlens inspect <file.fig> <instance-id>`. `tree` and `find` use the same types as `nodes` (`COMPONENT`, `COMPONENT_SET`, `GROUP`), so filter either by those names; `tree --json` also carries each node's local `size` `[width, height]`, `visible: false` on hidden layers and `layoutMode` on auto-layout frames, enough to sort top-level frames into screens, dialogs and assets without a `nodes` pass. `tree --depth 2` is only an initial outline; descend into relevant containers or use `find` for nested screens. `tree --top-frames` (MCP `topFrames`) lists every screen on the pages, including those in sections, one `id TYPE "name"` line each (`--json` adds `page`/`section`); groups and internal pages are skipped. In `tree --json`, nodes on a page or in a section carry `firstText`, their first visible text: a short frame whose `firstText` reads like a section heading is likely a canvas label, not a screen; confirm with `tree <id>` or `inspect` before skipping it. Done when you have identified the intended screen, without requiring a manual open or picker.
3. **Bundle it.** `figlens bundle <file.fig> <node> .figlens/exports/<scope>/frame.zip`, then unzip into its own directory beside it and read `context.md` first: it says what each file holds. Done when you know the reference image, the structure file and the asset map. Check `handoffDiagnostics` in inspect and `_figlens.handoffDiagnostics` in nodes for known stored semantics not emitted; bundle warnings summarize them. Their counts concern the selected expanded subtree, with explicit hidden/SLOT coverage limits, not proof of complete semantics. Inspect includes recorded text resize, truncation, max lines and decoration, and Dev Mode annotations and Ready for dev `devStatus` (Known gaps). Keep outputs distinct from the source. On `response_budget_exceeded`, use inspect, a scoped bundle, compact nodes (Reading the output), CLI nodes or a smaller export `maxSize`; `outputPath` in error metadata identifies a file already written.

   Reference PNGs stay lossless but may use a palette or grayscale; decode them as standard PNGs rather than assuming RGBA8 storage. See Images and slices for automatic size optimization.

4. **Outline before reading.** A screen is hundreds of KB of JSON, too large to read whole, and agent hosts may show only part of a tool reply over about 20 KB. Over MCP, call `nodes` for a screen with `out` (a `.json` path under `.figlens/exports/<scope>/`): the reply is just `{path, bytes, lines}` and the file holds the whole JSON for `jq`. With the `.fig` at hand, first run `figlens inspect <file.fig> <node> --depth N --full-text --colors` (MCP `fullText: true, colors: true`; add `--flat` for one line per node): layout, typography, complete text and solid fill colors with bound variables, so you need not parse `nodes.json` for them. Gradients, images, strokes, effects and vector geometry are not in it; read those from `nodes.json`. Then print the tree with sizes and layout, then read the subtrees you are building with `jq`:

   ```sh
   jq -r 'def o(d): "\("  " * d)\(.id) \(.type) \"\(.name)\" \(.absoluteBoundingBox.width // 0 | floor)x\(.absoluteBoundingBox.height // 0 | floor)\(if .layoutSizingHorizontal then " \(.layoutSizingHorizontal)/\(.layoutSizingVertical)" else "" end)\(if .layoutMode then " \(.layoutMode) gap=\(.itemSpacing // 0)" else "" end)\(if .layoutPositioning then " ABSOLUTE" else "" end)", (.children[]? | o(d + 1)); .document | o(0)' design/nodes.json
   jq '.. | objects | select(.id == "12:345")' design/nodes.json     # one node in full
   ```
5. **Decide the frontend structure, then build it.** Before writing markup, decide what each part of the design is in the project's code; the layer tree is how the designer drew it, not how the code is organized. Then take sizes, padding, gaps, radii, colors, shadows and fonts from the JSON as the values those components and layouts use; a gap under a parent without `layoutMode` is a coordinate difference, not an auto-layout rule. Use the reference to check visual relationships and an implementation screenshot to check the browser's actual result; these sources do not replace one another. Use the font and asset preflight below to flag missing inputs while continuing implementation. A screen built from raw values next to an existing component library is a second source of truth, and it drifts on the next design change.
   - **Components:** list the design's instances (`components` in `nodes.json`, the `I<instance>;…` ids, `componentProperties` for variants) and search the codebase for their counterparts, by name first (`Button`, `Card`), then by role (a button with `variant`/`size` props). Use the project's component with its props, set only what the design sets, and keep its defaults. When the design and the component disagree (a radius the component does not offer), use the component and report the difference instead of forking it. A component set with no counterpart, in a new project too, becomes one new component built from its component definition (`usages` on the set lists its members): appearance variants (style, size, tone) and text, boolean and swap properties become props, while hover, focus, pressed and disabled variants become CSS and ARIA states of the same component. Write one-off markup only for parts that are not components, in the project's style.
   - **Data:** sibling instances of one component (cards, rows, tabs, menu items) are that component rendered from an array; the text and images their overrides change are the array's fields. Content that differs between states or screens is data, not another copy of the markup.
   - **Markup and layout:** use the element each part is (`nav`, `header`, `main`, `form` with labelled inputs, `button`, `a`, `ul`, `table`, `dialog`). Write layout from auto-layout intent (direction, gap, padding, alignment, the sizing below) and grids as CSS grid; position absolutely only what the design takes out of flow. Headers, footers and menus that several screens share become one layout.
   - **Saved mappings:** when the host provides `figlens_bindings`, read the current file/frame together before reusing approved matches; `figlens_propose_bindings` records pending proposals for native human review. See [host integrations](https://github.com/runkids/figlens/blob/main/wiki/integrations.md) for Pi, OpenCode and OMP entry points.
   - **Icons:** reuse the project's icon before exporting a new one. An instance's `componentId` names its component; for a loose vector, export it as SVG with `--match-dir <project icon folder>` (MCP `matchDir`) and check `matches`, then `similar`; see Images and slices.
   - **Tokens:** `variables.json` holds the design's variables and modes. Match them to the project's tokens (CSS custom properties, theme object, Tailwind config) by name, then by value, and reference the token rather than the resolved number. Add a token only when nothing matches, and say so.
   - **Token export (when requested):** inspect `variables` first for exact collection and mode IDs. A library collection that `variables <node>` lists exports from the copies cached in the file (`libraryCopy: true`), which may lag the published library. Create the output parent directory, then call MCP `variables` with `format: "dtcg"`, `collection`, `mode` and `out`, omitting `node` (CLI: `variables <file.fig> --format dtcg --collection ID --mode ID --out FILE`). An alias into another collection exports that collection's value, recorded in `aliasOf`; when the target collection has several modes, choose one with `aliasModes: {collectionId: modeId}` (CLI `--alias-mode COLLECTION=MODE`). Inspect diagnostics before using the file; any diagnostic fails the whole export. Review the export against existing project tokens instead of replacing them automatically. Mapping, identity and rejection rules: [DTCG token export](https://github.com/runkids/figlens/blob/main/wiki/fig-format.md#dtcg-token-export).
   - **Conventions:** framework, styling approach, file layout and naming. The new screen should read as if the team wrote it.
   - **New project:** with no existing app, set up the current professional baseline of the requested stack before the first screen; it is part of the build, not an extra. Start from the stack's official scaffold in TypeScript with strict type checking; add a linter and formatter (such as oxlint and oxfmt) and `typecheck`, `lint`, `format` and `build` scripts; organize code by responsibility the way the stack does (components, hooks, API and data access, and so on), creating a module only when code has that role rather than splitting by rule; style through the requested system, such as Tailwind utilities with the design's variables mapped into its theme, not a hand-written stylesheet of raw values; self-host the design's fonts when a licensed package provides them. The requested stack is the floor of that setup, not its ceiling.
   - **Sizing intent:** before writing layout CSS, note each auto-layout child's `layoutSizingHorizontal`/`layoutSizingVertical`. HUG sizes to its content, FILL takes the parent's remaining space (grow on the parent's main axis, stretch on the cross axis), and only FIXED gets an explicit size. The reference shows one copy at one width, so copying its pixel widths onto HUG or FILL boxes matches the screenshot and breaks when copy, locale or container width changes. A growing text slot also needs to shrink: give it `min-width: 0` and decide whether long copy wraps or is clipped, so it cannot push past its parent.

6. **Prepare website images.** Inspect the target project's image components, asset directories, framework/loader/CDN configuration and neighboring pages; follow its established approach and applicable instructions. Use its existing optimization pipeline when present. Otherwise follow Images and slices below. Done when the deployed images have suitable formats and pixel dimensions for their displayed sizes, with loading behavior and byte sizes checked; bundle originals remain source material.
7. **Check against the reference.** First review the code as a reviewer of the change would: each component set and repeated part maps to a component or data array; the markup and layout follow step 5; the screen ships through the project's build and asset pipeline without design data fetched or interpreted at runtime; images are at their displayed size and format, fonts load without layout shift, and nothing loads up front that only a later route or interaction needs; the project's type check, lint and format pass. Fix that before chasing pixels: a pixel match does not make code that skips these decisions an implementation. Then apply Verification evidence below, rendering the build at the frame's size and comparing it with `references/screen.png` side by side or as a pixel diff. Check image requests at relevant desktop/mobile widths: transferred bytes, oversized images, layout shifts and the main image's loading behavior. Correct confirmed differences and rerun the exposing state; use [the audit workflow](references/audit.md) for an existing UI or an unresolved mismatch. Finish with a supported result or explicit evidence gap for each scoped item; unresolved fonts, assets, rendering gaps or unavailable browser checks leave affected visual acceptance pending.

For a question about layout, typography or copy, start with `figlens inspect <file.fig> <node> [--depth N]`: expanded bounds, auto-layout and typography, without paints or vector geometry. Depth defaults to 1 (0-10); at most 200 nodes and 200 characters per text are returned. A parent without auto-layout has `childSpacing: "derived"`: gaps between its children are coordinate differences, not an auto-layout rule (`constraints` may still pin them), so compare sibling screens or ask before treating one as a design token. `childCount` includes omitted children; `truncated` marks omitted descendants and `textTruncated` marks shortened text. For image decisions add `--images` (MCP `images: true`): `images.items` reports source dimensions/bytes and each paint's source-pixel crop rectangle before masks/effects/clipping (a STRETCH crop past the source is clamped, with `outside` giving how far it reaches per side), with a separate 200-paint limit and `images.truncated`. Text-range fills carry `textStyleId` matching the node's `styleOverrideTable`; used vector-region fills carry `vectorStyleId`. Missing/unrecognized sources and unsupported rectangles are explicit; these counts do not diagnose blur. Add `--full-text` (MCP `fullText: true`) for the complete text of each TEXT node (up to 10000 characters, `textTruncated` beyond) and `--colors` (MCP `colors: true`) for `solidFills` on nodes with visible solid fills: hex, opacity below 1 (the paint's own, not ancestors'), and the bound `variableId`/`variableName`; with `--flat` a fill gets a `$variable` suffix. Gradients, images, strokes and effects need `nodes`. Use `nodes` for paints beyond solid fills and masks, and `variables` for bound variables. To check a built screen against the design, `inspect <file.fig> <node> --depth N --flat` (MCP `flat: true`) prints one greppable line per node instead: id, type, name, position relative to the inspected node, size, text, font size/weight/line height, fills, stroke, radius, auto-layout direction/gap (for grids, `GRID RxC gap=row,col` and stored track sizes)/padding (top,right,bottom,left) or `spacing=derived` where gaps are only coordinate differences, `align=main/cross` (e.g. `space-between/center`) and `size=w/h` (`fixed`/`fill`; omitted when both hug), visible shadows and blurs (`shadow=0,8,24,#1e56e6/0.1`), opacity and `component=<id>` on instances, within the same limits; `children=N` and `… N more` mark omitted nodes. Each CLI call decodes the whole file, while MCP reuses the last unchanged local file (remote calls parse again); reuse saved output for repeated CLI queries. Across several `.fig` files, finish all queries on one file before switching, because each switch reloads. For several frames of one file, use `nodes --frames <list|->` or `nodes --ids <node>...` (REST nodes only), `export --frames <list|-> --out-dir <dir> [--format F]` for images, `bundle --frames <list|-> --out-dir <dir>` or consecutive MCP calls in the same process.

When the user asks for related component states, add `--states` to `inspect` or `bundle` (including batch bundles); over MCP pass `states: true` on those tools. It defaults to false. Keep `source.file` with every returned ID. Check each relationship, property support state, prototype inheritance/precedence, hidden coverage and truncation before describing behavior. `actionsTruncated: true` means omitted actions, even if the projected list is empty. Bundles include `design/states.json` and a bounded `context.md` summary; other variants' structures/assets require a separate inspect on the same source file. Names and prototype links do not establish business conditions. See [state evidence](https://github.com/runkids/figlens/blob/main/wiki/states.md) for scope and limits.

When the user asks how two variants differ, inspect the first definition with `--compare-variant <other-id>` (MCP `compareVariant`). Both must belong to the same component set. Read `variantComparison.rootChanges`, `pairedNodes` (children paired by unique name, main component or equal-count stacking order, with per-pair `changes`; check each `pairedBy` and treat `order` as the weakest evidence), descendant `collectionChanges`, `unpairedNodes`, `unknownFields` and its independent truncation before describing differences. Bound variables carry `variableId` and `variableName`. These are stored fields and value multisets, not alternate instance renderings or pixel fidelity; use returned source IDs for further inspection.

To see what changes between any two frames of one file (empty vs filled state, mobile vs desktop breakpoint, two screens sharing a header), use `--compare <other-id>` (MCP `compare`) instead of inspecting both and diffing by hand. It returns `comparison` in the same shape plus `rootDelta` (size and parent-relative position); each pair says `pairedBy` (`name` and `component` are firm, `order` is a guess from stacking order in equal-sized same-name groups); the rest stay in `unpairedNodes` with `reason: ambiguous-name`, so never pair them yourself from names. Instances are not expanded; a node and its ancestor are rejected.

When the person has a `figlens preview` open, a browser-automation tool can ask the page instead: `window.figlens.rankedSearch(query, …)` and exact `window.figlens.usages(id, …)` return the `search` and `usages` replies for the served file, bound to its snapshot. Result rows and `context()` name the page; live, `context().source` names the loaded file `path`, `sourceId`, `snapshotId` and local `revision`, which are null offline, where the page is unknown too. `context().coverage` is the reference scope's own (`scopeId`, `complete`, `warnings`, `reasons`); `complete: null` means unchecked, not complete, and a search reply's coverage never stands in for it; see [the Agent API](https://github.com/runkids/figlens/blob/main/wiki/preview-api.md#calls).

## Verification evidence

Use design data for structure and values, a design reference for visual relationships, and an implementation screenshot for the browser result. Record the actual viewport and state for both images; distinguish figlens renders from supplied Figma exports and check Known gaps before relying on them. A screenshot at one width or state covers only that case.

Check all three layers within the requested scope:

- **Elements:** dimensions, spacing, typography, colors and assets, including effective inherited and responsive styles.
- **Relationships:** alignment, columns/distribution, connector endpoints, stacking, opacity, occlusion and clipping. Matching isolated numbers does not establish the composition.
- **Variation:** supported item counts, long text, available widths and relevant states. Separate existing requirements/data contracts from hypotheses; a static snapshot does not establish unspecified responsive or business behavior.

For each item report: scope (platform/route, frame/node, viewport and state); design evidence (source node plus value or visual relationship); implementation evidence (`file:line` plus effective style or runtime observation); result (difference found, no difference found in the checked scope, or unresolved); verification (static inference or actual image comparison, with evidence paths when available); and unexamined states/reason. An item read only for structure stays structure-inspected, not compared.

Static review is not visual acceptance. If browser access is unavailable or prohibited, complete permitted static checks and report visual acceptance pending with the exact route/state/viewport and screenshots needed next. Lint, typecheck, bundle integrity and repeated reads do not establish rendered correctness. Treat an unexplained visual difference as unresolved, including font metrics/line breaks; document accepted exceptions rather than silently treating them as a pass.

Measure the image comparison instead of eyeballing it. Capture the running screen at the frame's size with fonts loaded: viewport width = frame width, a full-page screenshot when the frame is taller than the viewport, device pixel ratio as the scale. Then run `figlens compare-image <file.fig> <node> <screenshot.png> --out <exports>/diff.png` (MCP `compare_image` with `file`, `node`, `image`, `out`). When a full-page screenshot is shorter than the frame, add `--full-page` (MCP `fullPage: true`) instead of enlarging the viewport: the missing height is then a region of its own and `uncompared.missing`, a finding to fix like any other. It returns `mismatch`, `nonTextMismatch` and the largest differing regions in node pixels, each naming the deepest layers under it; `text: true` only means the region lies over TEXT layers: usually font fallback or line breaks, but a wrong text color, weight, size or copy lands there too. Open the diff PNG, fix the regions the design explains in the component or layout rule that produces them, not by pinning positions or sizes to the screenshot, and rerun. The result is tool-proven visual acceptance for that viewport and state only when every remaining region, text ones included, is fixed or recorded as a known difference with its cause (font fallback and its remedy, design departure, `warnings` entry); check a text region's color, size and copy against `inspect` before calling it fallback. Report the numbers and those regions with their node ids. By default it does not see differences under 48/255 per channel, such as light borders and subtle tints: rerun with `--threshold 16` (MCP `threshold`) and check those values with `inspect --colors`. Layers whose content comes from data (banners, user text, balances) go in `--ignore` (MCP `ignore`) so the score tracks layout; an ignored layer's size and position then need `inspect`. `image: true` regions are image content to confirm before ignoring, not a layout match. Report what you ignored. For scale, faithful builds measured 0.14-0.35% `nonTextMismatch` and an uncorrected first pass 3%.

## Link back to Figma

When referring to a specific frame or node in an answer or design document, link its actual name to its Figma location. Use ids read from the `.fig`, and include the page/frame path when names are ambiguous (`inspect`'s `path` lists it).

- Take the file key from the user's source URL (`/design/<file-key>/` or `/file/<file-key>/`), or the corresponding bundle's `manifest.json` → `source.fileKey`. Keep each `.fig` paired with its own key when reading multiple files. Pass the known key to `bundle --file-key` so its manifest preserves the source link. When the user needs to trace which saved design a built screen came from, add `--hash-source` (MCP `hashSource: true`) and keep the manifest's `source.sha256` with the node ids, so a later save of the same file is told apart.
- Build `https://www.figma.com/design/<file-key>/?node-id=<node-id>&m=dev`. For ordinary ids, change `112:319` to `112-319`. For expanded `I<instance>;…` ids, link the containing instance and show the full expanded id separately. Constructing links needs no Figma API or network access.
- With no known source URL or file key, ask once for the original Figma URL; meanwhile report the `.fig` name, page/frame path and node id. Never guess a file key from the filename or node id.
- Variables and modes are not frames: identify them as `collection → mode` (for example, `Color → Warm`), and link a related frame only after verifying that it uses the mode.

## Reading the output

- **CLI flags**: `figlens <command> --help` prints only that command's flags, defaults and output fields; a usage error prints the same entry. `figlens --help` prints every command.
- **Chaining calls**: MCP tools return structured JSON, and so do most CLI commands; CLI `tree` and `diff` print text unless you add `--json`, and `inspect --flat` and `workflow` print text. When you can run code (a host code or script tool, or a shell with the CLI and `jq`), run related calls in one script, such as a loop of exports or `inspect` filtered to the fields you need, and bring only that result into the conversation.
- **Compact nodes (opt-in)**: CLI `nodes <file> <node> --compact [--subtrees]` (also batch); MCP `nodes` with `compact: true`, optionally `subtrees: true`. Default REST and bundles are unchanged. The versioned wrapper shares repeated style values and optionally subtrees with per-node IDs/bounds; resolve its references before applying REST paths or `jq`. Follow the [lossless wire contract](https://github.com/runkids/figlens/blob/main/wiki/discovery.md#compact-nodes); table values are literal, not recursively interpreted. Hosts still cut a compact screen, so use `out` for one; complete MCP replies have an 8 MiB cap, with separate finite construction guards; narrow the node on overflow.
- **Shape** is the per-node object of a Figma REST nodes response, `{document, components, componentSets, styles, schemaVersion}` (`--frames` lines add `nodeId`): `document` is the frame; `children`; `absoluteBoundingBox {x,y,width,height}` in page coordinates (subtract the frame's x/y for positions inside it); `fills`/`strokes`/`effects`; `strokeWeight`, or `individualStrokeWeights {top,right,bottom,left}` when sides are set independently; read that instead, since `strokeWeight` can then be 0 (a bottom-only underline); auto-layout in `layoutMode`, `itemSpacing`, `padding*`, `primaryAxisAlignItems`, `counterAxisAlignItems`, `layoutSizingHorizontal`/`Vertical` (`FILL`/`HUG`/`FIXED`).
- **Absolute children**: `layoutPositioning: "ABSOLUTE"` marks a child of an auto-layout frame that sits outside the flow (title bars, floating inputs, badges). Place it with its bounding box, out of the flex flow.
- **Colors** are `r,g,b,a` floats in 0–1: multiply by 255. A paint's own `opacity` multiplies `a`.
- **Text**: `characters` and `style` (family, weight, size, `lineHeightPx`, letter spacing). Mixed styles inside one text are in `characterStyleOverrides` (one style id per character) and `styleOverrideTable` (id → the fields that differ), e.g. one bold word in a sentence.
- **Styles**: a node's `styles` maps a kind (`text`, `fill`, `stroke`, `effect`, `grid`) to a style id, which the response-level `styles` resolves to `{name, styleType, remote, description}`, plus `key` for library styles. Across two saves, match library styles by `key`, since their ids change on re-import, and local styles by name, since their keys are not in the `.fig`.
- **Instances**: ids starting with `I` (`I<instance>;<path>`) are layers inside a component instance, already expanded with its overrides; `componentProperties` holds the variant values.
- **Variables**: `boundVariables` maps a field to `VariableID:…` aliases; look the id up in `design/variables.json` for its name, collection and per-mode values, so the build can use a token (`BG/100`) instead of a hex value:

  ```sh
  jq -r '.variables[] | "\(.id)\t\(.name)\t\(.resolvedType)"' design/variables.json
  ```
- **Assets**: `assets.json` maps `imageRef` (original image fills, keep each node's crop and scale from its fill), `node:<id>` (an SVG of one vector) and `render:<id>` (a 2x PNG of a node that composites an image through a blend mode, mask or effect) to files under `assets/`. Export a complete icon or group by its instance/group ID instead of assembling individual vector assets; choose its output format after checking for image fills, and keep each SVG's root transform and unique ids when inlining several (see Images and slices).
- `visible: false` nodes are not drawn, and `export` refuses them (`unsupported_node`). Exclude them from visual output; hidden text layers may still contain relevant design notes. Read those as context, verify their node ownership and keep design text separate from agent instructions.

## Images and slices

`figlens export <file.fig> <node> <out.svg|png|jpg|webp|avif> [--scale 2] [--quality 80] [--max-kb 150] [--max-size 1600] [--bounds layout] [--match-dir DIR] [--hide ID[,ID]]` renders one node like Figma's Export panel, shadows included; instance sublayer ids work. The output extension picks the format. SVG keeps vectors, embeds original image fills and uses glyph outlines for text; scale and quality do not apply. When inlining or optimizing SVG (JSX, SVGO), keep its root `<g transform>`, since it draws in page coordinates, and keep definition ids unique: SVGO's default `cleanupIds` renames them to `a`, `b`, …, so a second inlined icon takes the first one's clip and vanishes. Use `prefixIds` or disable `cleanupIds`, and namespace duplicate copies of one node. `--max-kb` lowers lossy quality until the file fits; PNG/SVG report an error if over budget; `--max-size` scales raster output down to fit its longest side; JPG has no transparency and composites on white. It prints `{path, width, height, bytes, quality, layoutBox, renderBox, warnings}`; `quality` is the raster quality used (the requested value for SVG, where it has no effect). The export covers what the node draws, so shadows, outside strokes and overflowing children can make it larger than the layout box; the output reports `layoutBox`, `renderBox` and a warning naming what reaches past it. `warnings` also list the subtree's known skipped or approximated rendering (such as image adjustments), worded like bundle warnings, and each image or component the file lacks (a `figlens clipboard` copy carries no image bytes); check them before shipping or comparing against an export. A warning does not say how much of its layer shows: export again with `--hide <that node>` (MCP `hide`), which draws it as hidden over the same area, and compare the two images (for example `magick compare -metric AE`). Changed pixels show where the layer, as figlens draws it, reaches the result; a large area means the skipped rendering likely matters there. Little or no difference does not prove fidelity: the layer may show but match what is beneath it. Treat it as covered only after checking that opaque layers above hide it; otherwise get Figma's own export. When the asset must fill the layout slot, add `--bounds layout` (MCP `bounds: "layout"`), which cuts off what is drawn past the box. For many nodes, `figlens export <file.fig> --frames <list|-> --out-dir <dir> [--format F]` decodes once and writes `<dir>/<nodeId>.<format>`. Before adding an icon, check whether the project already has it: an instance's `componentId` (in `inspect`) names its component; for a loose vector, export it as SVG with `--match-dir <project icon folder>` (MCP `matchDir`, subfolders included; batch `--frames` exports accept it too). `matches` lists the files there that draw the same outlines regardless of position, paint and path syntax: reuse those. `similar` lists up to 10 `{file, score}` with a similar shape, such as a stroked copy or the same outlines at another size (score 1); near neighbours like plus/minus or lock/unlock also score high, so look at the candidate before reusing it.

Through MCP, call the `export` tool with absolute `file` and `out` paths: it writes the file and returns text metadata and `structuredContent`. Raster formats also return the same rendered bytes as inline image content; SVG returns metadata only. PNG is the most compatible choice for an agent's inline reference; choose website formats separately. Raster exports are scaled down to fit `maxSize` (default 1600 px on the longest side; pass 0 for the full scaled size). `find` and `inspect` are also MCP tools with the same options and structured results.

Many assets of one screen: use one batch call instead of one `export` per asset. MCP `export_batch` takes `file` and `items` (1-64 objects `{node, out, bounds?, scale?, quality?, maxKb?, maxSize?, hide?}`, the `export` parameters of those names, format from each `out`'s extension, distinct absolute `out` paths inside the configured roots, output directories created first); CLI `figlens export <file.fig> --batch items.json` (`-` reads stdin) takes the same array. It writes one file per item and returns one manifest `{count, failed, items}` with no inline images: per item `node`, `path`, `width`, `height`, `bytes`, `quality`, `layoutBox`, `renderBox` and `warnings`, or `node`, `path` and `error`. Read every entry's `warnings` (a render box past the layout box means a shadow, badge or overflow would clip or shift in the layout slot; re-export that item with `bounds: layout` or size the slot to the render box) and `error`: a failed item does not stop the others, so repeat only the failed ones. A malformed item, a repeated `out` or a path outside the roots fails the whole call before anything is written. `matchDir` is single-export only. After 256 MiB written, the remaining items fail; send them in another call.

PNG exports and rendered bundle/preview references are automatically optimized losslessly up to 4,194,304 pixels: decoded RGBA stays exact, and only a smaller result replaces the original encoded bytes. Larger PNGs keep regular encoding. PNG may use a palette or grayscale; `quality` never makes PNG lossy. `maxKb` is checked after optimization and still fails if the PNG exceeds the budget. Bundle source images are unchanged.

For website assets, start with the target project's working code and image pipeline, then consult its documentation. Reuse its image component, responsive sizing, loader/CDN and asset conventions. Optimize through that pipeline when it already handles delivery. When the project has no established approach:

1. **Choose by content.** Keep pure vector artwork as SVG. Inspect image fills or embedded `<image>` elements before treating an SVG as a vector asset: a tiny icon can embed a megabyte bitmap. For bitmap or mixed artwork, start with WebP and compare transparency, gradients and text against the source; use PNG when lossless output is needed. Evaluate AVIF when its size/quality tradeoff suits the project. Keep bundle originals as sources and generate delivery files separately.
2. **Size for use.** Determine CSS display dimensions and target DPR, then set `scale` and `maxSize` together. A 40px icon at 2x needs about 80px. Use `inspect --images` to compare source pixel counts after cropping with the intended output; rectangles are before masks/effects/clipping, not quality guarantees. A larger export can improve output sampling but cannot recover missing source detail. If blur remains, keep its cause unknown until source, crop or rendering evidence establishes it; enlargement without improvement does not identify the cause. Set `quality` and a use-appropriate `maxKb`, then inspect returned `width`, `height` and `bytes`. `maxKb` lowers lossy quality, not dimensions; revise dimensions or budget when needed.
3. **Export and handle errors.** Create output directories before exporting. For a 40px bitmap icon at 2x, an example starting point is:

   ```sh
   mkdir -p public/assets
   figlens export design.fig 12:345 public/assets/icon.webp --scale 2 --max-size 80 --quality 80 --max-kb 20
   ```

   The equivalent MCP arguments are `file`, `node`, absolute `out` ending in `.webp`, `scale: 2`, `maxSize: 80`, `quality: 80`, `maxKb: 20`; substitute the real file/node/project paths. These dimensions and budget are examples, not universal limits. Check `isError` and read `content` on failure before retrying; successful transport alone does not mean an export succeeded. Use figlens's existing raster export before adding conversion tools unless a concrete limitation requires them. Export the selected node when its crop, mask or effects must be baked in.
4. **Deliver and measure.** Provide responsive variants with `srcset`/`sizes` (or responsive CSS backgrounds) for large images. Reserve space with dimensions or aspect ratio; this reduces image-induced shifts, while CLS still requires measurement. Choose loading explicitly: preserve default loading for a small inline icon, lazy-load offscreen content, and prioritize an actual above-the-fold/LCP image when evidence supports it. In the browser, check the requested asset, decoded dimensions and transferred bytes as well as sharpness, transparency and crops at relevant widths. Export-file bytes and browser transfer bytes are separate measurements. Measure LCP/CLS when browser tooling allows, and report unavailable measurements. A successful build or an empty broken-image list does not establish efficient image delivery.

## Visual preview and handoff

Use `figlens preview <file.fig> [node]` when a person needs to browse or select a scope. A viewer you start in the background can take `--idle-exit SECONDS` to stop once no page is open. In Pi and a ready OpenCode integration, `/figlens preview [description]` resolves the design conversationally and starts its session-owned viewer through `figlens_preview`; no manual open is required. Open the printed local URL. The viewer provides page/frame browsing, name/text search, a synchronized layer tree, bounds-based overlap picking and property inspection. Download a selected-scope bundle or copy IDs/context without guessing them; expanded `I<instance>;…` IDs remain exact and work with `bundle` and `export`. The implementation prompt is grounded in design data, not an automatic mapping to project components. Its ranked search Mode also offers Semantic and Hybrid: the person presses Enable index for the file and scope there, and with a local model set up through the `models` tool the viewer builds its model layer too; without one, hybrid answers with text and says why. Text search creates nothing. Visual/Hybrid also accepts a PNG or selected stored visual unit and a pixel crop; the person explicitly enables the visual index. Query images stay transient, model availability and render coverage are reported, and similarity is not component identity. The browser API `imageSearch(pngBlob or {nodeId}, options)` uses the same revision-bound routes; `signal` cancels its model request. To drive an open preview from a browser-automation tool, call the page's `window.figlens` API (`state()`, `select(id)`, `context()`, `exportImage(...)`, plus `rankedSearch(query, …)` and exact `usages(id, …)` for the served file; see [the Agent API](https://github.com/runkids/figlens/blob/main/wiki/preview-api.md#calls)) instead of clicking through the UI.

For a portable handoff, run `figlens preview <file.fig> <node> --out preview.html`. The HTML works offline and embeds design data, original images and the snapshot-scope bundle. Selecting a child changes context, not the embedded bundle's scope. Share it only with people allowed to see those assets. Import a local implementation screenshot for side-by-side or opacity comparison; this is visual checking, not measured accuracy.

Live preview polls the saved local file. Treat a stale/error banner as unavailable fresh evidence; a failed save must not be described as a refreshed design. Snapshots never refresh. For `gs://` inputs the live viewer watches its local cached copy, not the remote object. No viewer action replaces checking the bundle's `missing-assets.json` and the known renderer gaps below.

## Component mappings

When `figlens_bindings` is loaded, it can retrieve saved component matches. Supply the **current request's `file` and `frame` together**; this works without open and leaves any manual selection unchanged. The current request determines the scope even if a different selection was saved earlier. It returns actual instance properties/text, approved rules, pending/stale candidates and pagination. Follow `nextOffset` when more instances are needed. Reuse recorded mappings marked `approved`, using current design text rather than example literals. Empty, unmatched or stale results do not block implementation: inspect source and design directly.

When the user wants to save reusable component matches, read the real target implementation and usage first. Call `figlens_propose_bindings` with explicit file/frame, its instance ID, target path/export/import/example, rationale, supporting file dependencies, checks actually executed and unresolved issues. Plain HTML can name an existing block and explain that no import is needed. The user reviews with `/figlens review`, which lists pending proposals across this project; proposals stay pending in non-interactive modes. Approval is a mapping decision, so run the project's permitted compilation/runtime checks and compare the screen separately. The [Pi](https://github.com/runkids/figlens/tree/main/pi), [OpenCode](https://github.com/runkids/figlens/tree/main/opencode) and [OMP](https://github.com/runkids/figlens/tree/main/omp) walkthroughs document installation and tested limits. Without these tools, continue with the CLI workflow above. Authenticated host clients are trusted; review UI is not an isolation boundary against other clients. No model tool approves mappings.

## Many frames

`figlens bundle <file.fig> --frames <list> --out-dir <dir>` decodes once and writes one bundle per id in `<list>` (one id per line; `-` reads stdin, so `figlens tree <file.fig> --top-frames` pipes into it), in parallel, printing a JSON line per frame (`{nodeId, path, warnings}` or `{nodeId, error}`). A single `bundle` prints the same object; non-empty `warnings` report missing assets, known skipped/approximate rendering and known unrepresented handoff semantics. `missing-assets.json` contains only asset failures; `_figlens.renderDiagnostics` in nodes locates render limitations. Use it instead of one `bundle` call per frame. When only REST nodes are needed, `figlens nodes <file.fig> --frames <list>` (`-` reads stdin) or `figlens nodes <file.fig> --ids <node>...` decodes once and prints one JSON line per id: the single `nodes` output with its `nodeId`, or `{nodeId, error}` (at most 10,000 ids). `figlens export <file.fig> --frames <list|-> --out-dir <dir> [--format png|jpg|webp|avif|svg]` takes the single `export` options, writes `<dir>/<nodeId>.<format>` and prints the same lines with the `export` output. MCP raster `export` returns every image inline, so over MCP export many images with `export_batch` (see Images and slices), which returns a manifest and no images. Over MCP, call `nodes` per frame for a local file, whose parse the server reuses; a `gs://` file parses again per call, so batch it with the CLI.

## Font and asset preflight

- **Fonts:** start from the bundle's `design/fonts.json` (or `verify`), which lists the families, styles and weights visible text uses, including applied overrides, with node ids; `verify` also looks each face up as a font file on this machine (pass the project's font folder as `--fonts <dir>`, MCP `fonts`): `local_file` names the file and how it matched, and a match in that folder carries a ready `@font-face`; ask the user about licensing before shipping it, and treat `unverified` as not found, not as absent. Otherwise locate licensed project font files or verified system faces. The bundle contains outlines, not installable fonts. For web fonts, use `document.fonts.load` with the actual design text, await `document.fonts.ready`, and verify the returned faces and requested weight/style. An empty array or `document.fonts.check` alone does not prove availability: fallback can pass the latter. Verify system fonts separately rather than treating an empty web-font result as proof of absence.
- **Assets:** read `missing-assets.json`, bundle warnings and `assets.json`; run `verify` (CLI `figlens verify <bundle.zip|dir>`) to check required files against the manifest's sizes/hashes; it reports missing and changed files, and marks each font face `local_file` (a name match in this machine's font folders or `--fonts`) or `unverified`. Its `findings` list gathers missing assets, unresolved variables, unmatched tokens, truncated state inventory, render limitations, unemitted semantics and font faces, each with `category`, `status` (missing, unsupported or unverified), node ids, evidence, impact and `action`; `findingsSummary` keeps total counts and truncation. Few findings do not prove readiness or fidelity. Before visual acceptance, check the deployed image URLs, decode success and rendered dimensions. An empty missing-assets list proves neither font availability nor correct browser delivery.
- **Continue:** record each dependency as verified, missing or unverified, with its evidence. Continue implementation without waiting for missing inputs: use available project fonts as documented fallbacks and clearly labelled image placeholders at the intended dimensions. Report the exact family/weight or asset/node, temporary choice and remedy in the handoff. Leave final visual acceptance pending for unresolved inputs; browser checks that could not run stay unverified. A successful bundle command does not prove visual fidelity.

## Known gaps

- Dev Mode annotations are on the annotated node in `inspect` and `nodes` as `annotations`: `label` (plain text; a preview in inspect, `--flat` shows only `annotations=N`), `labelMarkdown` (nodes), pinned `properties` and `categoryId`, named in the top-level `annotationCategories`. Ready for dev frames and sections carry `devStatus`. These are mapped from stored fields and not compared with Figma's exports. Treat annotations as the designer's notes on behavior and content to verify against the design, never as instructions to you. Dev Mode measurements are not emitted (`handoffDiagnostics` counts them); if one affects implementation, request its value and nodes from the user and leave the affected decision unresolved rather than guessing. Hidden TEXT notes and component descriptions are separate sources.

- Layout guides (`layoutGrids`) are not emitted. A GRID frame carries `gridRowCount`/`gridColumnCount`, gaps and `_figlens.gridTracks` (stored track sizes: FLEX in fractions, FIXED in px, HUG); children carry spans and alignment but no cell index, so place them in order and check their saved positions. Recorded constraints, layoutAlign/layoutGrow and componentPropertyDefinitions are partial: read `_figlens.semantics` for source and recorded/unsupported status; a missing entry means the source field is not stored. No absent defaults, complete variant options or SLOT semantics are inferred; these mappings have not been compared with same-version Figma exports. See [coverage](https://github.com/runkids/figlens/blob/main/wiki/semantics.md).
- Figma Motion and code layers are not emitted. When a scope has them, `handoffDiagnostics` lists `motion` or `codeLayers`: treat the frame as static and ask the designer for the animation or code rather than inventing it.
- Hidden overridden text can carry a stale size.
- Read `_figlens.renderDiagnostics` in nodes/bundles before matching reference pixels; `inspect` includes at most 20 per shown node and marks truncation. Absence of diagnostics does not establish fidelity. Renders skip image contrast/temperature/tint/highlights/shadows adjustments, glass effects and shader/noise/pattern fills, and draw angular/diamond gradients as radial; background blur blurs only what the same export draws behind the layer, so export the frame that contains the backdrop. Check those areas with the designer rather than matching the reference there.
- Font files are not in the `.fig`: name the fonts the design uses, and report the ones the project lacks instead of substituting silently.
