# OpenCode V2 integration

The single `@runkids/figlens` npm package exposes an OpenCode server entry, `./tui` and `./rpc`, alongside its CLI, Pi and OMP entries. The root stays CommonJS for the CLI; `opencode/` has its own module boundary. Local acceptance targets OpenCode 2.2.0. Other OpenCode generations are not covered.

Install the package in OpenCode V2:

```sh
opencode plugin add @runkids/figlens
```

For a local candidate, use the unpacked package directory as a `file://` URL. The package export lets the host load server and TUI entries separately. No other host SDK is imported by these entries.

Use `/figlens help`, or ask OpenCode to build a screen from a saved `.fig`. The shortcuts are `open`, `preview`, `plan`, `yolo`, `map`, `frame`, `status`, `review` and `close`. Plan authorizes a plan only; yolo authorizes implementation within the requested scope. Dispatch is not proof of model completion. Native TUI review shows evidence, edits all four target fields, resolves conflicts and confirms approval; noninteractive clients leave proposals pending. There is no model approval tool.

The server registers the shared skill and supplies a local `figlensmcp` MCP configuration only when neither a `figlensmcp` nor a `figlens` configuration exists; a user server under either key is used as configured. The managed key differs from `figlens` because OpenCode drops an MCP server whose name collides with the plugin's `figlens_*` tools. It preserves disabled, remote and local user overrides. Overrides whose version/snapshot cannot be verified block MCP-dependent shortcuts, while explicit local preview, frame selection, mappings and review remain available. When that user server is disabled, or is named `figlens` (which OpenCode drops), the plugin registers `figlens_index`, `figlens_jobs`, `figlens_search` and `figlens_inspect`, which run the same CLI commands, so the search flow below still works; the managed server or an enabled override serves those tools itself, so they are not registered twice. The managed default uses the same launcher and project directory as local operations; `FIGLENS_BIN` selects both paths. OpenCode is a Bun-built binary, so the bundled Node launcher runs with the `node` on PATH (Node 18 or later); `FIGLENS_BIN` bypasses it.

**Searching a design.** Ask OpenCode to find copy or a screen in a `.fig`: it searches the file directly and stores nothing. For repeated searches, ask it to *enable an index* for that design and a scope (for example "enable an index for ./design.fig, whole file"). The agent then calls `index` `prepare` with the file and scope, which creates a local workspace in the figlens state directory with no setup step, polls `jobs` until the build succeeds, and from then on searches the published index by `workspaceId` and `node` set to the chosen scope and opens results with `inspect`, also after a restart or from another host. Connecting, listing tools and ordinary searches create no database. `reset` and `replaceUnavailable` additionally ask OpenCode's `figlens_index` permission (resource `reset` or `replace_unavailable`) on both paths, so a session rule such as `{ "action": "figlens_index", "resource": "reset", "effect": "deny" }` blocks them while preparing and searching stay unprompted; the CLI path also asks `bash` permission for each command as before, and before a write it runs the read-only `index status` and asks `edit` permission on the workspace directory the binary reports (the state root while none exists) plus the config root; a `prepare` or `reset` that repairs a workspace whose status fails asks it for the place the failure reports; `jobs` `cancel` asks it for the job's workspace, and recreation for the new storage and the config root.

Indexes go to the figlens state directory, or to a location an earlier `--storage` prepare remembered, with no configuration. A new custom location is a filesystem choice: the managed MCP server refuses it, because it starts without `--storage-root`. To use one over MCP, configure your own `figlensmcp` local server with `["<figlens>", "mcp", "--storage-root", "/absolute/dir"]` and reload; OpenCode then treats it as a user override, as above. On the CLI path, a `storage` argument asks `edit` permission on that directory.

Server operations validate session/project ownership and request read/edit/bash permissions before side effects. Authenticated host clients are trusted: RPC does not prove that a human made the call. UI confirmation is a mapping decision, not a sandbox against other authenticated clients. Read/write errors, cancellation, stale evidence and writer contention remain errors.

Viewer URLs and design paths belong to the server machine. Reference attachments carry PNG bytes through the host file-content format; a textual path is not an image. Each session owns its viewer; deleting a session, reloading or unloading the plugin closes owned viewers. Client disconnect alone does not delete a durable session, so use `/figlens close` when finished. The adapter creates no tunnel.

Shared mapping files retain Pi's schema and human notes. See [Pi](../pi/README.md) for the underlying workflow and [integration acceptance](https://github.com/runkids/figlens/blob/main/wiki/integrations.md) for source-checkout checks.
