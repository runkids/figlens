# OpenCode V2 integration

The single `@runkids/figlens` npm package exposes an OpenCode server entry, `./tui` and `./rpc`, alongside its CLI, Pi and OMP entries. The root stays CommonJS for the CLI; `opencode/` has its own module boundary. Local acceptance targets OpenCode 2.2.0. Other OpenCode generations are not covered.

Install the package in OpenCode V2:

```sh
opencode plugin add @runkids/figlens
```

For a local candidate, use the unpacked package directory as a `file://` URL. The package export lets the host load server and TUI entries separately. No other host SDK is imported by these entries.

Use `/figlens help`, or ask OpenCode to build a screen from a saved `.fig`. The shortcuts are `open`, `preview`, `plan`, `yolo`, `map`, `frame`, `status`, `review` and `close`. Plan authorizes a plan only; yolo authorizes implementation within the requested scope. Dispatch is not proof of model completion. Native TUI review shows evidence, edits all four target fields, resolves conflicts and confirms approval; noninteractive clients leave proposals pending. There is no model approval tool.

The server registers the shared skill and supplies a local `figlensmcp` MCP configuration only when neither a `figlensmcp` nor a `figlens` configuration exists; a user server under either key is used as configured. The managed key differs from `figlens` because OpenCode drops an MCP server whose name collides with the plugin's `figlens_*` tools. It preserves disabled, remote and local user overrides. Overrides whose version/snapshot cannot be verified block MCP-dependent shortcuts, while explicit local preview, frame selection, mappings and review remain available. When that user server is disabled, or is named `figlens` (which OpenCode drops), the plugin registers `figlens_index`, `figlens_jobs`, `figlens_search`, `figlens_usages`, `figlens_diff` and `figlens_inspect`, which run the same CLI commands, so the search flow below still works; the managed server or an enabled override serves those tools itself, so they are not registered twice. The managed default uses the same launcher and project directory as local operations; `FIGLENS_BIN` selects both paths. OpenCode is a Bun-built binary, so the bundled Node launcher runs with the `node` on PATH (Node 18 or later); `FIGLENS_BIN` bypasses it.

**Searching a design.** Ask OpenCode to find copy or a screen in a `.fig`: it searches the file directly and stores nothing. For repeated searches, ask it to *enable an index* for that design and a scope (for example "enable an index for ./design.fig, whole file"). The agent then calls `index` `prepare` with the file and scope, which creates a local workspace in the figlens state directory with no setup step, polls `jobs` until the build succeeds, and from then on searches the published index by `workspaceId` and `node` set to the chosen scope and opens results with `inspect`, also after a restart or from another host. Connecting, listing tools and ordinary searches create no database. `reset` and `replaceUnavailable` additionally ask OpenCode's `figlens_index` permission (resource `reset` or `replace_unavailable`) on both paths, so a session rule such as `{ "action": "figlens_index", "resource": "reset", "effect": "deny" }` blocks them while preparing and searching stay unprompted; the CLI path also asks `bash` permission for each command as before and `read` on the design's requested and real path for search, inspect, prepare, add and relocate (for a workspace search, refresh or rebuild, on the registered designs `index status` reports, narrowed by `sourceId`), refuses a `gs://` design, whose download cache it cannot authorize (the MCP server reads those), runs builds until their jobs finish without the command timeout, and before a write it runs the read-only `index status` and asks `edit` permission on the workspace directory and the lock file beside it that the binary reports (the state root while none exists) plus the config root; a `prepare` or `reset` that repairs a workspace whose status fails asks it for the place and lock file the failure reports; `jobs` `cancel` asks it for the job's workspace, and recreation for the new storage and the config root.

**Finding usages.** Ask OpenCode where a component, variable, style or image is used: the agent calls the MCP `usages` tool with the exact layer or resource id, on the `.fig` directly (stateless) or, once an index is enabled, by `workspaceId`, the result's `sourceId` and the prepared scope; it never prepares, widens or resets an index for it. Results carry exact refs, a `snapshotId` and coverage; a hidden-layer exclusion or a source that changed is reported, not read as "unused". On the CLI path `figlens_usages` asks `bash` permission and `read` on the design (for a workspace, on the registered designs, narrowed by `sourceId`), as `figlens_search` does.

**Comparing revisions.** Ask OpenCode what changed between two saved copies of a design: the agent calls the MCP `diff` tool with `old` and `file` (local paths) and pages with `nextCursor`. Layers match by exact id and type only; `unknown` means a side stopped or left that layer unexpanded, not that it was removed. It reads both files and writes nothing. On the CLI path, `figlens_diff` asks `bash` permission and `read` on `old`, then on `file`, before it runs.

Indexes go to the figlens state directory, or to a location an earlier `--storage` prepare remembered, with no configuration. A new custom location is a filesystem choice: the managed MCP server refuses it, because it starts without `--storage-root`. To use one over MCP, configure your own `figlensmcp` local server with `["<figlens>", "mcp", "--storage-root", "/absolute/dir"]` and reload; OpenCode then treats it as a user override, as above. On the CLI path, a `storage` argument asks `edit` permission on that directory and its `state` directory. Every CLI-path `edit` ask also covers the real path a symlink on the way points to, since the binary writes there.

Server operations validate session/project ownership and request read/edit/bash permissions before side effects. Authenticated host clients are trusted: RPC does not prove that a human made the call. UI confirmation is a mapping decision, not a sandbox against other authenticated clients. Read/write errors, cancellation, stale evidence and writer contention remain errors.

Viewer URLs and design paths belong to the server machine. Reference attachments carry PNG bytes through the host file-content format; a textual path is not an image. Each session owns its viewer; deleting a session, reloading or unloading the plugin closes owned viewers. Client disconnect alone does not delete a durable session, so use `/figlens close` when finished. The adapter creates no tunnel.

Shared mapping files retain Pi's schema and human notes. See [Pi](../pi/README.md) for the underlying workflow and [integration acceptance](https://github.com/runkids/figlens/blob/main/wiki/integrations.md) for source-checkout checks.
